# 2장: 자바 메모리 영역과 메모리 오버플로

- 자바에서는 JVM이 제공하는 자동 메모리 관리 메커니즘 덕에 메모리 할당 & 해제를 짝지어 코딩하지 않아도 메모리 누수나 오버플로 문제를 겪을 일이 거의 없음.
- 통제권을 위임했기 때문에 문제가 한 번 터지면 가상 머신이 어떻게 메모리를 관리하는지 그 방식을 이해하지 못하는 한 해결하기가 어려움.
- 2장에서는 JVM이 관리하는 다양한 메모리 영역을 소개함.

## 런타임 데이터 영역
- JVM이 관리하는 메모리는 자바 프로그램을 실행하는 동안 필요한 메모리를 몇 개의 데이터 영역(런타임 데이터 영역)으로 나눠서 관리.
- 이 영역들은 각각 목적과 생성/삭제 시점이 존재.
  - 어떤 영역은 가상 머신 프로세스의 시작과 동시에 만들어지고
  - 어떤 영역은 사용자 스레드의 시작/종료에 맞춰서 생성/삭제 된다.
- 런타임 데이터 영역
  - 전역(모든 스레드가 공유하는 데이터 영역)
    - 메소드 영역
      - 런타임 상수 풀
    - 힙
  - 스레드별 데이터 영역(스레드 프라이빗)
    - 가상 머신 스택
    - 네이티브 메서드 스택
    - 프로그램 카운터(pc) 레지스터

### 프로그램 카운터
- 프로그램 카운터 레지스터는 작은 메모리 영역으로 현재 실행 중인 스레드의 `바이트코드 줄 번호 표시기`라고 생각하면 됨.
  - 바이트코드 인터프리터는 카운터의 값을 바꿔 다음에 실행할 바이트코드 명령어를 선택하는 식으로 동작.
  - 즉, 프로그램의 제어 흐름, 분기, 순환, 점프 등을 표현
  - 예외 처리나 스레드 복원 같은 모든 기능이 이 표시기를 활용해서 이뤄짐.
- JVM에서 멀티스레딩은 CPU 코어를 여러 스레드가 교대로 사용하는 방식으로 구현되기 때문에 특정 시각에 각 코어는 한 스레드의 명령어를 실행한다.
  - 따라서 스레드 전환 후 이전에 실행하다 멈춘 지점을 정확히 복원하려면 스레드 각각에 고유한 프로그램 카운터(어디까지 실행했는지 체크하기 위해)가 필요.
  - 따라서 각 스레드의 카운터는 서로 영향을 주지 않는 독립 영역(스레드 프라이빗 메모리)에 저장된다.
  - 스레드가 자바 메서드를 실행 중일 때는 실행 중인 바이트코드 명령어의 주소가 프로그램 카운터에 기록된다.
  - 스레드가 네이티브 메서드를 실행 중일 때 프로그램 카운터 값은 Undefined임.
  - 프로그램 카운터 메모리 영역은 <자바 가상 머신 명세>에서 OutOfMemoryError 조건이 명시되지 않는 유일한 영역임.

### 자바 가상 머신 스택(JVM 스택)
- JVM 스택도 스레드 프라이빗 -> 연결된 스레드와 생성/삭제 시기가 일치
- 각 메서드가 호출될 때마다 JVM은 스택 프레임(메서드 실행 도중 사용되는 기본적인 데이터 구조)을 만들어 지역 변수 테이블, 피연산자 스택, 동적 링크, 메서드 반환값 등의 정보를 저장.
- 그 다음 스택 프레임을 가상 머신 스택에 푸시(push)하고 메서드가 끝나면 팝(pop)하는 일을 반복함.
- 자바 메모리 영역은 힙/스택 메모리로 구분짓기 어려울 정도로 복잡함.
  - 보통 자바를 논할 때 언급하는 스택은 자바 가상 머신 스택을 가리키는 경우가 많은데, 그 중에서도 특히 지역 변수 테이블을 지칭하는데 쓰임
- 지역 변수 테이블에는 JVM이 컴파일 타임에 알 수 있는 다양한 기본 데이터 타입, 객체 참조, 반환 주소 타입을 저장한다.
- 일반적으로 슬롯 하나의 크기는 32비트임. 따라서 double 타입처럼 길이가 64비트인 데이터는 슬롯 2개를 차지하고 나머지 타입은 모두 슬롯 하나에 저장.
- 지역 변수 테이블을 구성하는데 필요한 데이터 공간은 컴파일 과정에서 할당된다.
- 자바 메서드의 경우, 스택 프레임에서 지역 변수용으로 할당받아야 할 공간의 크기가 이미 완벽하게 결정되어 있음. 
  - -> 메서드 실행 중에는 해당 공간(변수 슬롯 개수)의 크기가 절대 변하지 않는다.
- 가상 머신이 변수 슬롯을 구현하는데 사용하는 메모리의 실제 크기는 가상 머신을 어떻게 구현하느냐에 따라 완전히 달라질 수 있음.
  - 슬롯 하나가 32/64 비트 또는 그 이상일 수도.
- 자바 가상 머신 명세는 스택 메모리에서 두 가지 오류가 발생할 수 있도록 정의함.
  1. 스레드가 요청한 스택 깊이가 가상 머신이 허용하는 깊이보다 크다면 StackOverflowError를 던진다.(스택 넘쳤으니까)
  2. 스택 용량을 동적으로 확장할 수 있는 JVM에서는 스택을 확장하려는 시점에 여유 메모리가 충분치 않다면 OOM을 던진다.

### 네이티브 메서드 스택

- 네이티브 메서드 스택은 가상 머신 스택과 매우 비슷한(지역 변수 테이블, 피연산자 스택, 동적 링크, 메서드 반환값 등의 정보를 저장) 역할을 함.
- 차이점이라면 가상 머신 스택은 자바 메서드(바이트코드)를 실행할 때 사용하고 네이티브 메서드 스택은 네이티브 메서드(C/C++)를 실행할 때 사용한다는 것.
  > ### 네이티브 메서드?
  > - 네이티브 -> 해당 체제를 만들 때 사용한 프로그래밍 언어를 뜻함.
  > - 자바 런타임은 C로 만들어졌음.
  > - 따라서 자바 기준에서 네이티브 -> C/C++ 를 의미.
- 자바 가상 머신 명세에서는 네이티브 메서드 스택에서 어떤 구조로 어떻게 표현해야 하는지에 대해 아무 것도 명시 X -> 구현자가 자유롭게 표현 가능.
  - 그래서 네이티브 메서드 스택과 가상 머신 스택을 하나로 합쳐놓은 가상 머신도 있음.
- 얘도 똑같이 스택 허용 깊이를 초과하면 StackOverflowError / 스택 확장에 실패하면 OOM을 던진다.


### 자바 힙
- 자바 애플리케이션이 사용할 수 있는 가장 큰 메모리임.
- 자바 힙은 모든 스레드가 공유하며 가상 머신이 구동될 때 만들어짐.
- 이 메모리 영역의 유일한 목적은 객체 인스턴스를 저장하는 것.
  - 자바 세계의 `거의` 모든 객체 인스턴스가 이 영역에 할당됨.
  - 자바 가상 머신 명세에서도 "모든 객체 인스턴스와 배열은 힙에 할당된다"고 적혀 있음.
- 근데 왜 `거의`일까? -> 탈출 분석 기술이 발전하면서 스택 할당과 스칼라 치환 최적화 방식이 달라짐.
- 자바 힙은 가비지 컬렉터가 관리하는 메모리 영역이기 때문에 GC 힙이라고도 한다.
- 대다수 현대 가비지 컬렉터는 세대별 컬렉션 이론(generational collection theory)를 기초로 설계됐다.
- 힙을 설명할 때 아래와 같은 용어들이 자주 등장.
  - `신세대(new generation)`, 
  - `구세대(old generation)`, 
  - `영구 세대`, 
  - `에덴 공간(eden space)`, 
  - `생존자 구간에서부터(from survivor space)`
  - `생존자 구간으로(to survivor space)`
- 이와 같은 영역 구분은 가비지 컬렉터들의 일반적인 특성 또는 설계 방식일 뿐, 반드시 이 형태로 메모리를 구성해야 한다는 뜻은 아니라는 점.
- G1 컬렉터가 등장한 2010년 전후로 핫스팟 가상 머신은 업계에서 확고한 주류로 자리 잡음.
- 핫스팟의 가비지 컬렉터들은 모두 신세대 컬렉터와 구세대 컬렉터를 조합해 동작하는 전통적인 세대 구분을 따랐음.
